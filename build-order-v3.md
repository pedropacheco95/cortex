# Cortex v3 — Build Order (codebase-understanding round)

**Status:** v3 implementation sequence. Separate from `build-order.md` (v1.0, design §16.2) and `build-order-v2.md` (the v2 foundation) — both of those shipped records stay frozen. Same discipline as v1 §16.2 / build-order-v2: shared substrate before the pieces that depend on it, one dev spec (or a small coordinated set) per step, each independently verified and dogfooded on this repository before the next begins (RULES 14 — never "here are the specs, build it all"). Dependency order, not a schedule.

**This build order is layered on the shipped v2 foundation.** The v3 build begins **after** the v2 foundation ships; it does not disturb in-flight v2 work. Two consequences, stated up front:

- **build-order-v2 steps 6–8 are frozen** (design §2.2, §8.4) — the two v2 insight loops (`cortex-loop-insight-refresh`, `cortex-loop-insight-gaps`) and the promotion accept path. They are **not extended, not deleted**. The v2 insight code that has already landed stays in place as **interim dogfood** — it keeps working and stays useful — until v3's insight (step 5) replaces it wholesale, at which point the frozen steps retire with it.
- **All other v2 work continues unchanged** — schema 2.0, the `.specflow/` reorganization, the query-CLI substrate, and the typed pulse-gate / promotion extensions. None of it is insight-specific; all of it is foundation v3 builds on. Design §8.2 names precisely what is salvaged (the typed pulse gate + promotion plumbing; the `cortex insight` command dispatch, `--json` convention, and deterministic-Core-reads-files execution model) and §8.3 what is dropped (the `map/` layout; the `query/get/neighbors/list` verbs; the v2 constellation preset).

**Depends on:** `cortex-schema-v3-addendum.md` being drafted and reviewed first — it is **step 1** below, and both Core and Skills build against it. Its scope is fixed by design §10.1; this order does not draft it. Also depends on `cortex-v3-design.md` (reviewed and signed off).

---

## The sequencing spine

Two load-bearing sequencing facts govern this order.

**(1) The schema addendum is the contract; the module rename re-roots everything downstream.** Every v3 piece names the final module set (`compass`, not `cerebrum`; `insight` per the new layout; `archive`; `provenance`). So the schema 3.0 addendum (step 1) and the module migration (step 2) come first, and everything after them builds against the final names. Archive's change-plan gate proposes to `compass`/`atlas`/specs; provenance's `derives_from` resolves to `compass` rules and `atlas` decisions; the insight CLAUDE.md block says "compass rule," not "cerebrum." All of that assumes step 2 has landed.

**(2) The version-gate activation is coupled to the rename (the v2 step-1 idiom, resolved).** Schema v3.0 is a MAJOR bump. The addendum (step 1) is the **contract document** — drafted and reviewed. The **version-gate wiring** (project `cortex.config.json` → `3.0`; validator `supportedMajor` → 3; the re-rooted `check.compass-*`) is *code* and lands **coupled with the module migration in step 2**, exactly as v2 coupled its `2.0` bump to the `.specflow/` reorg (build-order-v2 step 1, the §16.3 coordinated-change idiom). Bumping the config to 3.0 activates the re-rooted compass checks; a bump before the rename (or a rename before the bump) leaves the repo failing its own validation mid-step, so they MUST land in the same commit with the re-rooted validator run against the renamed tree as the round-trip regression. The **new-module checks added later** (`check.archive-*` step 3a, `check.insight-*` step 5b, `check.provenance` step 4) must each be written to **tolerate an absent module** — the v2 precedent (`check.layout` "when its module is present") — so `cortex validate` passes at 3.0 before archive/insight content exists.

**(3) One apparent circularity, resolved: archive step-7 needs provenance.** Design §10.2 lists Archive (3) *before* Provenance (4), yet says provenance is "wired into archive's step-7 plan application." The resolution: step 3 builds the archive module and the ingestion skill **including** the 8-step workflow, but step-7's `derives_from` **stamping** is completed in step 4 (provenance). Archive ships plan-application that *creates* rules/specs/decisions; step 4 adds the provenance stamp those created artefacts carry. This mirrors v2's contract-then-producer sequencing and keeps each step independently verifiable.

## Steps

**Implements:** `schema.version-3` (the addendum itself; per RULES 19 the addendum carries its own change report enumerating every check/clause it touches).
**depends_on:** — (first; both layers depend on it).
**Done when:** the addendum is written, internally consistent with `cortex-schema.md` v2.0, its change report enumerates every re-rooted and new check/clause, and Pedro has reviewed and signed off. No code changes in this step.
**Split:** one document, one review. Not a `/goal` build batch — a design/authoring pass, like v2's Artefact 2.

### 2. Module migration — `cerebrum`→`compass`, decisions single-home, version-gate activation
**Builds:** the in-place migration (design §4) plus the coupled version bump. (a) the directory move `cerebrum/`→`compass/` and the path-constant + `check.*` re-root across Core (every `check.cerebrum-*`→`check.compass-*`, the PreWrite enforcement read, layout checks, node-id grammar module-path spellings — rule/bug ids `R-NNN`/`B-NNN` and their content-keyed node prefixes are **unchanged**), the scaffolding re-root (CLAUDE.md managed block, each `_index.md` naming cerebrum, `loop.md` wording, hook payloads, the "Modules present" line), and the skill/loop text re-root (`cortex-loop-rule-decay`, `cortex-pulse-distil`, `specflow-bugs`, and every other bundle naming `cerebrum/`); (b) the decisions single-home — `cerebrum/decisions.md` is excluded from 2a's directory move entirely and never exists at `compass/decisions.md`; delete it directly from its original `cerebrum/decisions.md` location as its own step after 2a has landed (**removed**, not renamed-then-removed), and where a compass rule's body inlined the duplicated decision text, replace the inline copy with a `derives_from: atlas/decisions/<slug>.md` citation (rules with no decision linkage untouched — but the citation form itself is finalized in step 4, so step 2 removes the duplicate and leaves a plain reference that step 4 upgrades to validated provenance); (c) the version-gate activation — `cortex.config.json` → `3.0`, validator `supportedMajor` → 3, run the re-rooted validator against the renamed tree as the round-trip regression.
**Implements:** `migration.compass-rename`, `migration.decisions-single-home` (the module-migration spec, §10.3).
**depends_on:** 1.
**Done when:** the repo's `.cortex/cerebrum/` lives at `.cortex/compass/`, `cortex validate` passes at `schemaVersion 3.0` against the renamed tree with zero errors, no `cerebrum` path constant or check name remains in Core or skill text (grep-clean), `cerebrum/decisions.md` is gone with no orphaned decision content, and — per RULES 19 — the change report enumerates **every** check and clause the rename touched (the "reported 3, touched 9" failure mode is precisely what this rename risks). Dogfooded on this repo (which runs Cortex on itself).
**Split:** **YES — likely two sub-batches** (coordinated-change idiom): 2a = the compass rename + path/check/scaffolding/skill re-root + version-gate activation + regression; 2b = decisions single-home (delete the duplicate, convert inline copies to citations). Keep them separate so 2a's validator regression is green before touching decision content. The two are sequenced within the migration spec so the decisions file is removed rather than renamed-then-removed (design §4.2).

### 3. Archive module + ingestion skill
**Builds:** the `archive/` module (design §6). Sub-step 3a = the module layout (`_index.md`, `register.md`, `documents/<slug>/` with `source.*` + `metadata.yaml` + `extracted/`, `types/`), the `metadata.yaml` contract (`ingested_at`, `version`, `supersedes`), the `archive/types/*.yaml` document-type schema format and how the skill routes on it, `cortex init` scaffolding of the module, and the three validator checks `check.archive-layout` / `check.archive-metadata` / `check.archive-type` (each tolerant of an absent module per the spine). Sub-step 3b = the `cortex-archive-ingest` skill: type routing (declared or inferred), the 8-step workflow (invoke → classify → store source → extract into `extracted/` → inline clarifying questions → **the yes/no change-plan gate** → apply approved plan → register update), and the document-version-update diff path (§6.5). The change plan at step 6 is proposed and human-approved **through the salvaged v2 pulse gate** (design §8.2) — ingestion never mutates gated content autonomously (RULES 7). Ingested documents are authoritative by definition, so extraction writes structured content **directly** into the document's `extracted/`, not into pulse.
**Implements:** `archive.module` (3a), `archive.ingest-skill` (3b) (the archive ingestion skill spec, §10.3).
**depends_on:** 2 (the change-plan gate targets `compass`/`atlas`/specs — final names; and 3a re-roots against the migrated tree). 3b additionally depends on the salvaged v2 pulse gate (already shipped).
**Done when:** `cortex init` scaffolds `archive/` (committed), the three checks flag a malformed document dir / bad metadata / unknown type and pass a well-formed one, and a dogfood run of `cortex-archive-ingest` on a real document classifies its type, stores the source verbatim under `documents/<slug>/`, extracts structured content into `extracted/`, honours the yes/no gate (No → ingested-as-reference, no downstream proposals; Yes → drafts a plan routed through the pulse gate), and updates `register.md`. **Note:** step-7's `derives_from` stamping on created artefacts is completed in step 4, not here (see spine fact 3).
**Split:** **YES — two sub-batches:** 3a = module layout + `types/*.yaml` schema + `metadata.yaml` contract + three checks + init wiring (Core/validator work); 3b = the skill (type routing + 8-step workflow + yes/no gate + version-update diff). 3b is a Light batch on its own; split its extraction-strategy routing out if it overruns.

### 4. Provenance — frontmatter, check, backward-traversal index
**Builds:** the provenance system (design §7). The `provenance:` list frontmatter field with `derives_from:` entries on **compass rules, both spec trees, and atlas decisions**; the three source-type reference forms (`archive/documents/<slug>/...`, `claude-sessions/<user>/<id>`, `atlas/decisions/<slug>.md`) with their resolution semantics (archive/atlas references must resolve; `claude-sessions` references are cited-not-resolved); `check.provenance` (validates resolvable references, absence means "authored directly" not "unknown origin"); and the **backward-traversal index** (source → derivations) that §6.5 step 3's version-update reverse-lookup consumes. Then **wire it into archive's step-7 plan application** — every rule/spec/decision the ingestion skill creates carries `derives_from` back to its source document — completing the archive workflow deferred from step 3 (spine fact 3), and upgrade the step-2b decision citations to validated provenance.
**Implements:** `provenance.frontmatter-check` (the provenance spec, §10.3).
**depends_on:** 1 (field defined in the addendum), 2 (targets compass/atlas), 3b (the archive step-7 it wires into). Provenance reuses the existing v1/v2 curated citation-graph machinery (schema §6) — same frontmatter-cross-reference mechanism, same reference-resolves validator machinery; the one new capability is the backward index.
**Done when:** `check.provenance` flags an unresolvable `archive`/`atlas` reference and passes a resolvable one and a `claude-sessions` cited-not-resolved reference; the backward index returns every artefact deriving from a given source; an archive ingestion run stamps `derives_from` on the artefacts its plan creates; and a superseded-document run (§6.5) uses the reverse-lookup to surface downstream rules/specs for review. Dogfooded on a real compass rule that derives from an atlas decision.
**Split:** one Light batch (field + check + index), plus the archive-wiring which is small. Split the backward index out if the wiring crowds the batch.

### 5. Insight rebuild — the centre of gravity
The largest item, broken into five sub-steps in dependency order. Consumer-before-producer throughout (the CLI, 5c, is built before the extraction skill that produces what it reads, 5d — the v2 design §13 idiom). Salvages the v2 CLI plumbing (command dispatch, `--json`, deterministic-Core-reads-files) per design §8.2; only the verbs change.

#### 5a. Level 1 structural extraction — in Core
**Builds:** the deterministic L1 pass (design §5.2, RULES 3 — no LLM, runs **in Core**): tree-sitter parse (RULES 18, the only parser), import/export graph, file sizes, entry points, module structure, **centrality analysis**, and the study's **skip-lists** (`node_modules`, build dirs, lockfiles) + sensitive-file patterns as pre-triage, plus "exclude mechanical hubs from centrality." This is the raw material the planning phase (5d) consumes.
**Implements:** `insight.l1-structural`.
**depends_on:** 1.
**Done when:** L1 runs on this repo producing an import/export graph + centrality ranking in minutes, skip-lists exclude the right paths, mechanical hubs are excluded from centrality, and output is deterministic (byte-identical across runs on unchanged input).
**Split:** one Light batch (deterministic Core, single pass).

#### 5b. Insight storage layouts + per-file entry contract + validator checks
**Builds:** the `.cortex/insight/` scoped and flat layouts (design §5.8) — `scope-registry.yaml`, `scopes/<scope>/{anatomy,concepts,graph.json}`, top-level `anatomy/`, `concepts/`, `graph.json`, `tags.json`, `clusters.json`; the per-file entry frontmatter + section contract (§5.5 — Purpose / Main players / Insights / File map / Connections / Query pointers); the `_index.md` active prompt (§5.13); the staleness ledger (`built_at_commit` + per-entry hashes) + reverse-dependency-index storage shape; and the new validator checks (`check.insight-*`, each tolerant of an absent module per the spine). Contract-first: the checks precede the producers that must satisfy them (5d, 5e).
**Implements:** `insight.storage-format` (the insight storage-format spec, §10.3).
**depends_on:** 1. (L1's output, 5a, is one of the things stored, but the storage *contract* is schema-defined and can be built and checked against hand-authored fixtures without L1 running — see flag F5 below.)
**Done when:** `cortex init` scaffolds `insight/` + `_index.md` (committed, not gitignored — §5.1); a hand-authored per-file entry + minimal JSON trio + a scope-registry validate clean; the checks flag a malformed entry (bad frontmatter, missing section, wrong JSON shape, non-total-ordered serialization) and pass a well-formed one; and the refuse-to-shrink-without-`--force` guard rejects a truncating write.
**Split:** one Light batch (formats + checks over defined schema); split init-wiring out if it fights the format work.

#### 5c. `cortex insight file/concept/element` query CLI
**Builds:** the three deterministic query subcommands (design §5.6) — `cortex insight file <path>` (rich per-file entry), `cortex insight concept <name>` (files touching a concept + related concepts), `cortex insight element <query>` (atomic element, or "no rich entry" when not an L3 main player) — all with `--json`, all **deterministic Core reading pre-extracted files** (RULES 3, no LLM at query time). Reuses the salvaged v2 command dispatch, `--json` convention, and execution model (§8.2); retires the v2 `query/get/neighbors/list` verbs (§8.3). Built before the producer so it is testable against hand-authored fixtures and becomes the verification surface 5d/5e use.
**Implements:** `insight.cli` (the `cortex insight` CLI spec, §10.3).
**depends_on:** 5b (formats to read).
**Done when:** all three subcommands run against a hand-authored fixture `insight/` (scoped and flat), `file` returns the rich entry, `concept` returns the touching files, `element` returns a main player and correctly reports "no rich entry" for a non-main-player, `--json` emits stable structured output, and the layer hides the scoped-vs-flat difference (same query works against both layouts, §5.8).
**Split:** one Light batch (three thin read-only commands over defined formats).

#### 5d. `cortex-extract-insight` skill — the plan-not-pipeline initial extraction
**Builds:** the extraction skill (design §5.3, §5.4, §5.11) — invoked from Claude Code sessions and scheduled tasks, **no CLI wrapper** (RULES 3: agentic work lives in a Skill). Sub-step 5d-i = **planning**: consume L1 output, draft the extraction plan (logically-coherent scopes, nesting, shared sub-scopes) to `.cortex/pulse/insight-extraction-plan.md`, build the **scope registry** (`scope-registry.yaml` — path, `depends_on`, `shared_by`), the same-module-vs-similar-module dedup judgment, recursion for oversized scopes, and the auto-run-threshold / present-plan-for-review gate. Sub-step 5d-ii = **scoped execution + unification**: one parallel sub-agent per root scope doing per-file L2 (purpose + connections) + scope-local-centrality-selected L3 (main players / insights / quirks / file map), shared scopes extracted once, then the Phase-4 **cross-scope L4 unification** agent (concepts / patterns / cross-scope edges) — with the study's defensive-orchestration contract (parallel sub-agents in one message; write-fragment-to-disk-then-merge; disk-file-is-success-signal; missing fragment = warn-don't-silently-skip; >half missing = abort), resumability/checkpointing per scope, progress to `.cortex/pulse/insight-extraction-progress.md`, and output validation against 5b's checks.
**Implements:** `insight.extract-skill` (the `cortex-extract-insight` skill spec, §10.3 — the load-bearing one).
**depends_on:** 5a (L1 output to plan against), 5b (writes to the storage contract), 5c (the CLI is the verification surface).
**Done when:** a dogfood extraction on a small real codebase produces schema-valid per-file entries + concepts + the JSON trio (green under 5b's checks), `cortex insight file/concept/element` (5c) returns them, a scoped run on a larger tree writes a plan + registry, extracts shared scopes once, and cross-scope unification produces edges spanning scopes; a killed-and-resumed run recovers from checkpoints without re-doing completed scopes; determinism disciplines hold (stable IDs, total-ordered serialization).
**Split:** **YES — two sub-batches:** 5d-i = planning (L1 consumption + scope registry + recursion + plan/threshold gate); 5d-ii = scoped execution + cross-scope unification + resumability + progress. Each a Light *build* batch. **Runtime-orchestration flag:** the skill's own runtime fan-out (top-level agent → per-scope sub-agents) is one level and fine; the recursion in §5.4 must be handled by the top-level orchestrator **re-planning** (breaking a scope and re-dispatching from the top) rather than a scope sub-agent spawning its own sub-agents, so the runtime respects the same one-level fan-out limit the build orchestration does until the writer/verifier harness lifts it (flag F7).

#### 5e. The three insight-refresh loops
**Builds:** the maintenance system (design §5.9, §9) — `cortex-loop-insight-refresh-fast` (post-commit, deterministic, no LLM: flags changed files, no extraction — the structural significance filter lives in **Core**, RULES 3), `cortex-loop-insight-refresh-daily` (significance triage = Core structural filter + Haiku on the uncertain cases; L2 on any real change; L3 on significant change; L4 neighbourhood updates around L3 re-extractions), and `cortex-loop-insight-refresh-full` (weekly, configurable — full L4 regeneration as ground truth). Plus the three Cortex-original refresh requirements the study's DIFFERENTLY verdicts demand: the **reverse-dependency index** (a changed file invalidates every concept/edge referencing an entity in it), **confidence-aging** (an INFERRED edge un-reconfirmed across N refreshes surfaces for re-verification), and **scope-scoped invalidation** (a changed file re-plans only its owning scope(s) + touching cross-scope edges). Each loop follows the loop-write invariant (RULES 7 / v2 §4.4): it maintains machine-owned ungated insight directly and proposes nothing gated.
**Implements:** `insight.refresh-loops`.
**depends_on:** 5a (fast loop's structural flagging + the Core significance filter), 5b (writes storage + the staleness ledger / reverse index shape), 5d (an initial extraction must exist to refresh).
**Done when:** a commit flags the right files (fast, no LLM); a daily run triages significance (structural filter rules out formatting/comment/whitespace/import-reordering; Haiku classifies the rest), re-extracts L2 on real changes and L3 only on significant ones, and neighbourhood-updates L4; a full run regenerates L4 deterministically; the reverse index invalidates referencing concepts/edges on a change; confidence-aging surfaces a stale INFERRED edge; and scope-scoped invalidation leaves untouched scopes cached. Registers the three scheduled tasks; deregisters the v2 insight-refresh/gaps pair (the frozen build-order-v2 steps 6–7 retire here).
**Split:** **YES — likely two sub-batches:** 5e-i = the three loops' extraction/triage tiers (fast/daily/full + significance filter); 5e-ii = the reverse-dependency index + confidence-aging + scope-scoped invalidation (the anti-silent-drift machinery). 5e-ii depends on 5e-i's loops existing.

### 6. `cortex-loop-session-observe`
**Builds:** the session-observation loop (design §9, §5.5) — the v3 successor to v2's `insight-gaps`, refocused from codebase-gap-signals to session observation. Reads recent Claude Code session transcripts (the **shared session corpus**, coordinated with `cortex-pulse-distil` and the read-time purpose capture of §5.10) and infers durable knowledge (corrections, gotchas, non-obvious behaviour, established patterns). Routes **by type**: ungated codebase observations enrich the relevant insight per-file entries (the *Insights* and *Query pointers* sections) **directly** — insight is machine-owned and ungated (RULES 7's machine-owned-ungated allowance), carrying `claude-sessions/<user>/<id>` provenance; gated conventions/rules are proposed to **compass** and decisions to **atlas** through the **pulse gate** (human-reviewed, RULES 7), reusing the salvaged v2 pulse-gate/promotion machinery (§8.2). Its boundary with `cortex-pulse-distil`: distil mines cross-session repetition into rule candidates; session-observe captures in-context per-session observations — shared corpus, different altitude (exact division of labour is a spec-pass detail).
**Implements:** `insight.session-observe` (the `cortex-loop-session-observe` spec).
**depends_on:** 5d (per-file entries must exist to enrich), 5b (the storage + provenance-stamped entry contract), 4 (the `claude-sessions/*` provenance form + the pulse-gate proposal path for gated content), and the salvaged v2 pulse gate (shipped). Effectively depends on the insight rebuild (5) being in place.
**Done when:** a dogfood run over recent session transcripts routes correctly — an ungated codebase observation lands in the right per-file entry's *Insights*/*Query pointers* section with `claude-sessions/*` provenance and touches no gated content, while a gated convention/rule surfaces as a typed compass proposal and a decision as a typed atlas proposal (never a direct gated write); and the distil-coordination boundary is proven not to double-propose. The `insight-gaps` session-observation role is preserved; only its v2 mechanism/five-gap-signal framing is gone (the frozen build-order-v2 step 7 retires here).
**Split:** **YES — likely two sub-batches:** 6a = collect + type-routing judgment + ungated insight enrichment (direct writes with provenance); 6b = the gated pulse routing (compass/atlas typed proposals) + distil-coordination boundary. 6b leans on step 4 and the salvaged gate being green.

### 7. Anatomy deprecation
**Builds:** the anatomy→insight transition (design §5.10, §9). Sub-step 7a = **re-point the consumers**: `specflow-develop`, `specflow-tests`, the hooks, and `cortex-loop-spec-drift` read `insight` instead of `.cortex/anatomy/` (anatomy's file listing/structural graph → insight L1; purpose lines → insight L2; `spec_links`/`governs:` → insight Connections; `purpose_source` → insight extraction metadata, with read-time purpose capture — v1's PreRead/PostRead cycle — integrated into insight tagged `read-time` provenance). Sub-step 7b = **retire the producers and the module**: deprecate the `cortex-loop-anatomy-refresh` (deep) + fast variant (replaced by the step-5e refresh loops), deregister their scheduled tasks, and remove `.cortex/anatomy/`. Sequenced so consumers re-point as content moves — **7a before 7b**, so nothing reads a module that has been removed.
**Implements:** `migration.anatomy-deprecation`.
**depends_on:** 5 (insight must hold anatomy's content — specifically 5a for L1 structure and 5d for L2 purpose entries — before consumers re-point). Read-time capture integration additionally coordinates with 6 (session-observe reads the same corpus).
**Done when:** develop/tests/hooks/spec-drift query insight and no code path reads `.cortex/anatomy/`; the anatomy-refresh loop pair is deregistered; `.cortex/anatomy/` is removed; and `cortex validate` passes with anatomy absent. RULES 15's gitignore note for `.cortex/anatomy/` is retired in the same change. Dogfooded: this repo's develop/tests/spec-drift runs use insight.
**Split:** **YES — two sub-batches:** 7a = re-point read consumers + migrate read-time purpose capture into insight; 7b = retire the anatomy-refresh loop pair + deregister tasks + remove the module. 7a strictly precedes 7b.

### 8. Skill integrations — the `cortex insight` enrichment pass
**Builds:** the follow-up enrichment pass (design §5.12), mirroring v2's SpecFlow-awareness pass landing after the substrate ships (build-order-v2's out-of-scope note): add explicit `cortex insight` invocations to skill workflows — `specflow-develop` (query insight for every file it plans to modify before writing; query the concept before cross-file changes — the biggest lever), `specflow-change-router` (query insight to understand what a change touches), `specflow-tests` (query insight for testing conventions before generating), `specflow-ingest` (query insight before proposing spec changes), and `specflow-onboard-codebase` (coordinate with insight extraction — deeper, probably last). Not integrated: `specflow-lint`, `specflow-viewer`, `specflow-bugs` (design §5.12).
**Implements:** `insight.skill-integrations`.
**depends_on:** 5c (the CLI must exist for skills to invoke) — effectively the insight rebuild (5). Independent of 6/7, so it may land any time after 5c.
**Done when:** each integrated skill invokes the right `cortex insight` verb at the right workflow point (dogfood: a `specflow-develop` run on this repo queries insight before editing), and the non-integrated skills are unchanged.
**Split:** one Light batch per skill if needed; the five integrations are independent and can be sequenced as separate shallow batches under the depth constraint.

### 9. Ingestion re-home — fold atlas-only `cortex-ingest` into archive
**Builds:** the fold-in (design §6.6) — the v1/v2 `cortex-ingest` skill's atlas-only ingestion (raw sources → `atlas/sources/`, extracting stakeholders/decisions/domain terms) re-homes into `cortex-archive-ingest` as its **atlas-routing extraction strategy**: sources land under `archive/documents/<slug>/source.*` (not `atlas/sources/`), atlas extractions become one type-routed strategy within the one ingestion skill, and atlas-derived decisions get the same provenance chain as everything else. ## Orchestration-depth constraint

Per `standing-authorities.md` (the temporary constraint, in force until v1 §16.2 step 11 — the writer/verifier harness — ships), every `/goal` batch runs `specflow-develop` at **Minimal or Light depth**: no sub-agent-spawns-sub-agent. Steps whose scope exceeds one Light batch MUST be split into sequential sub-batches (each its own shallow develop run), not delegated deeper — flagged above for steps 2, 3, 5d, 5e, 6, 7. If any nominally-single step overruns mid-build, split it the same way rather than deepening the orchestration. **Two extra cautions specific to v3:**

- **The `cortex-extract-insight` skill (5d) is itself an orchestrator.** Its *runtime* fan-out (top-level agent → one sub-agent per root scope) is one level and permitted, but §5.4's recursion for oversized scopes must be implemented as **top-level re-planning** (the orchestrator breaks a scope and re-dispatches from the top), NOT as a scope sub-agent spawning its own sub-agents — otherwise the recursive extraction fails silently under the same platform limit that scopes this constraint. This is a design requirement on the 5d spec, not just a build-time note (flag F7).
- **Step 5 is the round's largest block.** Even at Light depth its five sub-steps (several themselves split) span multiple rounds; sequence them strictly (5a → 5b → 5c → 5d → 5e) and keep each sub-batch's verification (the 5c CLI over hand-authored fixtures, then over real extraction output) green before the next.

## Sequencing decisions made here that the design left implicit (each flagged)

- **F1 — Version-gate activation lives in step 2, not step 1.** Design §10.1 lists "Version wiring" as a schema-addendum clause. But the addendum (step 1) is the *contract document*; the *activation* (`config → 3.0`, validator `supportedMajor → 3`, re-rooted `check.compass-*`) is code that must be coupled to the rename so the repo never fails its own validation mid-step. I place activation in step 2, mirroring v2's step-1 coupling of the `2.0` bump to the `.specflow/` reorg. New-module checks added later (3a/4/5b) are written absent-module-tolerant so 3.0 passes before those modules exist.
- **F2 — Archive is split 3a/3b and its step-7 provenance stamping is deferred to step 4.** Design §10.2 orders Archive (3) before Provenance (4) yet says provenance is "wired into archive's step-7." I resolve the apparent circularity: step 3 builds the archive module (3a) and the full 8-step ingestion skill (3b) that *creates* downstream artefacts, and step 4 completes the `derives_from` **stamping** on those artefacts. Archive is verifiable at step 3 without provenance stamping; step 4 finishes the loop.
- **F3 — Insight (5) is sub-stepped 5a–5e with an explicit consumer-before-producer order.** Design §10.2 states insight as one bullet. I break it into L1-Core (5a) → storage+checks (5b) → CLI (5c) → extract skill (5d, itself 5d-i/5d-ii) → refresh loops (5e, itself 5e-i/5e-ii). The CLI precedes the extraction skill (v2 §13 idiom) so it is testable against hand-authored fixtures and becomes the producer's verification surface. 5e is split into the loop tiers and the anti-silent-drift machinery (reverse index / confidence-aging / scope-scoped invalidation).
- **F4 — Ingestion re-home (9) is parallelizable, kept late.** It depends only on 3b + 4 and has no dependents, so it could land right after step 4. I keep it at step 9 (design's order) as a cleanup, but flag that it may move earlier.
- **F5 — 5b depends on 1, not on 5a.** The insight storage contract and its validator checks are schema-defined and testable against hand-authored fixtures without L1 having run; L1's output (5a) is *content that gets stored*, not a prerequisite of the *storage contract*. This lets 5a and 5b proceed in either order after step 1 (I list 5a first because 5d needs both).
- **F6 — Anatomy deprecation (7) is strictly 7a-before-7b.** Consumers must re-point to insight *before* the anatomy module and its refresh loops are removed, so no code path reads a deleted module. The design says "sequence so those consumers are re-pointed as anatomy's content moves"; I make the within-step order explicit and add that RULES 15's `.cortex/anatomy/` gitignore note retires in 7b.
- **F7 — The `cortex-extract-insight` recursion must re-plan from the top, not spawn nested sub-agents.** The orchestration-depth platform limit applies to the skill's *runtime* recursion (§5.4), not just to build-time `specflow-develop`. I flag this as a design requirement on the 5d spec: recursion is top-level re-planning, keeping runtime fan-out to one level until the writer/verifier harness lifts the constraint.
- **F8 — Step 2 is split 2a/2b so the decisions-single-home change follows a green rename regression.** Design §4.2 says the migration spec "sequences the two changes so the file is removed rather than renamed-then-removed." Resolved: `cerebrum/decisions.md` is excluded from 2a's directory move outright and never exists at `compass/decisions.md`; 2b deletes it directly from its original `cerebrum/decisions.md` path, as its own step once 2a is green. I make that two sub-batches (2a rename + version, 2b decisions), and note that the inline-copy→citation conversion in 2b lands as a plain reference that step 4 upgrades to validated provenance (since `check.provenance` doesn't exist until step 4).
