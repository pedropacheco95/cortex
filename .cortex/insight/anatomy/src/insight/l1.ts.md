# src/insight/l1.ts

## Purpose

The deterministic Level-1 structural pass: walks the repo applying skip-lists/sensitive patterns/`.gitignore`/config excludes, tree-sitter-parses every included source file, resolves the relative-import graph, groups files into directory-level modules, and produces a degree-centrality ranking with mechanical hubs excluded from the ranking (but not from `files`). No LLM, no timestamps, no randomness — output is byte-identical across runs on unchanged input; persistence is explicitly NOT this file's job (that's insight.storage-format).

## Main players

- `runL1` (lines 307–422) — orchestrates the full pass: walk, per-file parse, import resolution, edge building, module grouping, and centrality ranking. [critical]
- `walk` (lines 113–172) — recursive directory walker producing sorted included/skipped path lists; applies skip-dir/sensitive-dir/ignore filters and never follows symlinks. [critical]
- `serializeL1` (lines 429–463) — stable, timestamp-free JSON serialization of an `L1Output` for downstream persistence. [critical]
- `resolveImportSpec` (lines 276–290) — wraps l1-parse's `resolveImport` with a NodeNext-style `.js`→`.ts` (etc.) variant fallback. [supporting]
- `packageEntryCandidates` (lines 181–225) — derives entry-point path candidates from package.json `main`/`module`/`bin`, including dist→src and extension-variant mappings. [supporting]
- `reexportSpecs` / `exportedNames` (lines 235–261) — JS/TS-only regex supplements recovering re-export sources and `export const`-style names that the l1-parse tree-sitter walk misses. [supporting]

## Insights

Centrality ranking deliberately excludes mechanical hubs from the *ranking* only — hub edges still count toward neighbours' degree, and hub files remain in `files` (lines 398–401); undercounting hubs' own rank without erasing them from the graph. Symlinks are never followed (line 128) — an explicit determinism/cycle-safety choice, not an oversight. The tree-sitter walk in l1-parse.ts misses re-export specs and lexical-declaration (`export const x =`) exports, so this file supplements it with two JS/TS-only regexes (`reexportSpecs`, `exportedNames`) rather than fixing l1-parse — the "one resolution contract" is still `resolveImport` in l1-parse.ts; this file only adds a NodeNext-aware wrapper around it, never a second resolver.
